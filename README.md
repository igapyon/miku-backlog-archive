# miku-backlog-archive

Backlog の内容をローカルに保存し、静的 HTML 一式として閲覧できるようにするツールです。

課題や Wiki、添付ファイル、共有ファイルを手元に残し、Backlog に接続しなくてもプロジェクトの内容を読めることを目指します。

## 開発状況

ローカルのアーカイブ作業領域を初期化・検証し、Backlog からプロジェクト、課題、コメント、参加者、関連課題、現在版 Wiki、課題・Wiki 添付、共有ファイルを収集する CLI 基盤を実装しています。
収集済みデータだけから、ホーム・課題・Wiki・ファイルの最小静的 HTML も生成できます。本文では、保存済み添付を指す限定的な Backlog 記法と課題添付画像記法をローカル資産へ変換し、取得済みの課題・Wiki への限定的な内部リンク、見出し・リスト・引用・コードフェンスの安全な最小表示にも対応しています。外部画像は取得・自動読込しません。共有ファイルの本文リンク、Backlog/Markdown の完全な互換表示、Material Web による画面の仕上げは未実装です。
検討事項と実装予定は [TODO.md](TODO.md) を参照してください。

## 基本構想

Backlog からデータを取得する処理と、保存データから HTML を生成する処理を分けます。
Backlog との通信には `miku-backlog-api` を利用します。
データベースは使わず、保存データと取得の進捗は JSON などのファイルで管理します。

```text
Backlog
  ↓ miku-backlog-api による取得
ローカルの保存データ（JSON・添付ファイル・共有ファイル）
  ↓ HTML 生成
静的 HTML 一式
  ↓
ブラウザーでオフライン閲覧
```

保存データから HTML を再生成できる構成にし、表示の改善だけであれば Backlog からの再取得を不要にします。

選択した対象範囲の全件取得を基本とし、完了済みアーカイブに更新内容を差分反映する機能は対象外とします。
取得途中で中断した場合は、保存済みデータと進捗記録を使い、未完了の取得から続きを再開できるようにします。
再開は同じアーカイブ作成を完了させるための機能です。完了後に最新の内容を保存する場合は、新しい全件取得として扱います。

製品名の `archive` は、内容を保存して後から閲覧する用途を表します。
Backlog への復元は、将来の拡張を含めて恒久的な機能対象外です。本ツールは一方向の閲覧用アーカイブであり、完全な復元用バックアップとしての保証はありません。

## 想定する利用場面

主用途は、完了したプロジェクトを後から参照できる形で保存することです。課題の経緯、Wiki、添付ファイル、共有ファイルを、Backlog への接続を前提にせず閲覧できる状態で残します。

進行中のプロジェクトでは、リリース、移行、体制変更などの節目に、その時点の内容を別のアーカイブとして保存します。完了したアーカイブは更新せず、後の時点を保存する必要がある場合は新しい全件取得を作成します。

このツールは日常的な同期、Backlog への復元、法令・規程上の保存要件を満たすことの保証を目的にしません。生成物の保管場所と共有範囲は利用者が管理します。

## 初期対象と仕様案

初期リリースでは、指定した 1 プロジェクトの課題・コメント・Wiki・課題と Wiki の添付ファイル・共有ファイルを取得対象とします。
共有ファイルは Backlog の「ファイル」機能にあるもので、フォルダ構成とファイル本体を保存し、生成 HTML の一覧から辿れるようにします。
Wiki や課題・コメントの本文中に表示される画像も取得・保存し、生成 HTML でオフライン表示できるようにします。
対象プロジェクトの添付画像を含め、本文中の画像参照をローカルの保存先に変換します。外部サイトや対象外プロジェクトの画像は初期版で取得しません。詳細は [docs/inline-images.md](docs/inline-images.md) を参照してください。
以下はこの対象範囲をもとにした仕様案です。保存項目の詳細や画面構成は引き続き検討します。

| 項目 | 案 |
| --- | --- |
| 取得単位 | 指定した 1 プロジェクト |
| 課題 | 完了済みを含む課題、本文、属性、コメント |
| Wiki | ページ本文 |
| 添付ファイル | ファイル本体を保存し、画像もローカルで表示 |
| 共有ファイル | 「ファイル」機能のフォルダ構成とファイル本体を保存 |
| 本文中の画像 | Wiki・課題・コメント中の画像を保存し、HTML からローカル参照で表示 |
| HTML | プロジェクト目次、課題一覧・詳細、Wiki 一覧・詳細、共有ファイル一覧 |
| 内部リンク | 取得済みの課題・Wiki・添付ファイル・共有ファイルへの参照を相対リンクに変換 |
| 閲覧方法 | `index.html` を直接開く。必要な CSS・JavaScript も同梱 |
| 取得記録 | 取得開始・終了日時、対象、取得件数、失敗・未取得の項目を記録 |

課題の保存項目と個人情報の扱いは [docs/issue-data.md](docs/issue-data.md) を参照してください。

メニューに対応する機能の範囲は次のとおりです。

| 機能 | 対応方針 |
| --- | --- |
| ホーム・課題・Wiki・ファイル | 初期版の対象 |
| ガントチャート | 初期版には含めず、STEP2（仮称）での対応を目指す |
| ボード | 一旦対象外 |
| Git／Subversion（プルリクエストを含む） | 対象外 |
| プロジェクト設定 | 対象外 |
| ドキュメント | 対象外 |
| 課題の追加 | 不要。実装しない |

課題はコメントに付随する変更記録まで、Wiki は取得時点の現行版までを初期版の対象とします。詳細は [docs/history-scope.md](docs/history-scope.md) を参照してください。

## 保存と閲覧の考え方

- API が返すデータを保存し、HTML 生成時に必要な情報を取り出せるようにします。
- 保存対象は、使用する認証情報の権限で取得できる範囲です。
- 取得中にも Backlog の内容は更新され得るため、取得期間を記録します。単一時点の完全なスナップショットを保証する設計ではありません。
- 取得失敗や対象外の参照を記録し、不完全な取得を完了扱いしない方法を検討します。
- 大量取得は直列に行い、408・429・5xx などの一時失敗は、1秒・2秒の待機を挟んで初回を含め最大3回試行します。最終的な失敗は進捗に記録し、次回の収集で再開します。
- 再開時は取得元と対象プロジェクトを照合し、完了済みの取得を利用します。保存途中のデータや添付ファイル・共有ファイルは完了済みとして扱いません。進捗の記録単位と再取得の範囲は今後設計します。
- API キーなどの認証情報は、保存データや生成 HTML に含めません。
- 生成 HTML は Backlog のアクセス制御を引き継がないため、保存先・共有先で閲覧範囲を管理します。

## メニューとディレクトリ構成の方針

- 閲覧対象のメニュー名・順序・分類は Backlog のプロジェクトメニューに倣います。初期対象に対応する基本メニューは「ホーム」「課題」「Wiki」「ファイル」とします。
- 対象外の機能と「課題の追加」はメニューに設けません。ガントチャートは STEP2（仮称）で対応する際に追加します。
- 生成 HTML のディレクトリ階層とページ配置も Backlog の URL 体系に倣い、元のページと保存先の対応が分かる構成にします。
- 元の URL、リソース ID、ローカルの保存先を対応づけ、取得済み対象へのリンクを相対リンクに変換します。コメントなどのページ内参照も対応を設計します。
- `file://` で直接閲覧できるように、リンク先には HTML ファイル名を明示します。拡張子、URL のクエリやフラグメント、ファイル名として使えない文字の扱いを含む具体的な対応規則は今後決めます。
- API の保存データと進捗記録の配置は、HTML の再生成・取得の再開に適した形で [アーカイブ形式 v1](docs/archive-format.md) として定義します。

## 現在利用できる CLI

Node.js 22 以降で、依存ライブラリを追加せずに実行できます。`init` と `verify` は Backlog に接続せず、`runtime verify` は Runtime ファイルだけを検証します。`collect` は実行時環境の認証情報を使って Backlog を読み取り専用で収集します。

```sh
node src/cli.mjs init \
  --output ./my-archive \
  --source-domain example.backlog.com \
  --project-key DEMO
node src/cli.mjs verify --output ./my-archive
node src/cli.mjs runtime verify --runtime ./miku-backlog-api-runtime-0.7.10.mjs
# BACKLOG_DOMAIN と BACKLOG_API_KEY を実行時環境へ設定した後に実行する
node src/cli.mjs collect \
  --archive ./my-archive \
  --runtime ./miku-backlog-api-runtime-0.7.10.mjs
node src/cli.mjs render --archive ./my-archive
node src/cli.mjs report --archive ./my-archive
```

`init` は空の出力先だけを受け付け、既存ファイルを上書きしません。`collect` は manifest のドメインと実行時の `BACKLOG_DOMAIN` を照合し、課題・コメント・参加者・関連課題、現在版 Wiki、課題・Wiki 添付、共有ファイルのフォルダ構成と本体を取得します。`render` は完了済みアーカイブの保存データだけを使い、`site/index.html` 以下を生成します。`report` は完了前でも実行でき、保存済みの進捗から `site/collection-status.html` を生成します。API キーをファイルへ書き込んだり、コマンド引数で指定したりしません。作成するファイルと中断に耐える書き込み方法は [アーカイブ形式 v1](docs/archive-format.md) を参照してください。

## デザイン方針

- 静的 HTML のデザイン基準は Material Design 3 とします。
- UI コンポーネントには Material Web（`@material/web`）を利用します。
- Material Web で足りない部分は、`local-html-tools/lht-cmn` の `lht-*` コンポーネントのデザインや実装を参考にします。踏襲は必須とせず、本プロジェクトの閲覧用途に合わせて設計します。
- 配色、レイアウト、文字組み、情報の密度は今後決めます。
- Material Web を含む必要な CSS・JavaScript と、使用するフォント・アイコンなどはローカルで利用できる形に揃えます。閲覧時に CDN などへの接続を必要とせず、`file://` での動作を検証します。

## リポジトリ運用

- `workplace/` は、外部リポジトリのクローン、取得結果、検証用の生成物などを置くローカル作業領域です。`workplace/.gitkeep` 以外は Git で管理しません。
- `.codex/skills/` は Codex スキルのローカル配備先です。スキルのソースが必要になった場合は、別の正規の保存先で管理します。
- `node_modules/`、ビルド生成物、テストカバレッジ、ローカルの VS Code MCP 設定は Git で管理しません。共有が必要な MCP 設定は、認証情報を含めない例示用ファイルまたはドキュメントとして管理します。
