# Wiki 本文の添付参照を補完する計画

状態：P0 の実 API 調査を完了。画像補完の実装は未着手・保留。

## 目的と確認済みの事実

Wiki 本文に `![image][1074278457]` のような数値参照があるのに、Wiki 本体と添付一覧のメタデータに対応する添付がない場合を扱う。

対象 Wiki は `2092298`。保存済み本文には `1074278455`～`1074278459` の5つの異なる `![image][ID]` 参照があるが、どのIDにも対応する `[ID]: URL` 定義がない。保存済み Wiki の添付と Wiki 共有ファイルはどちらも0件で、miku-backlog-api v0.8.0 と Backlog REST API の Wiki 添付一覧も HTTP 200・空配列だった。

5つの参照IDすべてへ `download_wiki_attachment` を各1回実行し、Runtime 経由ではすべて HTTP 404（診断コード `UPSTREAM_ERROR`）だった。Runtime 内の `getWikiAttachment` は仕様どおり `GET /api/v2/wikis/:wikiId/attachments/:attachmentId` を呼ぶ。独立した REST クライアントから同じ本体 URL を確認する試行は接続タイムアウトとなり、状態コードを取得できなかった。追加照会は行っていない。

Nulab のヘルプが示す Wiki 添付画像記法は `#image(ID)`、Markdown の画像記法は `![Alt](URL)` である。対象本文の `![image][ID]` は参照スタイル Markdown の形だが、対応する参照定義がない。Nulab の説明にあるどちらの記法にもそのまま一致しない。Wiki 本体の API 応答には `attachments` と `sharedFiles` が含まれ得るが、対象データでは両方とも空だった。

現状の証拠では archive の一覧取得処理が添付や Wiki 共有ファイルを取り落としたとは言えない。数値参照から添付本体を直接取得する処理を加えても、この5件は同じエンドポイントで404になる。本文の数値は現在の添付IDではなく未解決の参照ラベルである可能性が高い。ただし404だけで削除済みとは断定しない。5件はいずれも本体を取得できていないため、P1～P5の回復実装へは進まず、まず原文の参照定義または実際の画像 URL／添付IDの由来を確認する。

miku-backlog-api v0.8.0 は `get_wiki_attachments` と `download_wiki_attachment` を公開している。archive は未解決参照がある Wiki の一覧を追加照会し、一覧と Wiki 本体から得た添付だけをダウンロードしている。本文参照の抽出自体は実装済みである。

## 採用する方針

一覧が空でも本体取得できるか、また対象IDが添付IDなのかを先に調べる。今回の5件は Runtime からすべて404となり、Wiki 本体にも添付・共有ファイルがなく、本文参照定義もない。このため、今回の Wiki ID と参照IDを使う自動補完は実装しない。原文に URL 定義が見つかるか、Backlog で同じ画像に対応する有効な添付IDまたは Wiki 共有ファイルが確認できた場合に、P0を再評価してから P1～P5 を開始する。

通信は固定 Runtime の `openDownload` と `allowedPermissions: ['READ']` を使用する。archive 製品に直接 REST API を呼ぶ経路は追加しない。保存済み Wiki のプロジェクトIDを照合し、その Wiki ID と本文参照IDの組み合わせだけを取得候補にする。他の Wiki、課題、共有ファイル、外部 URL を探索しない。

## P0：本体取得と Runtime の応答を確認する

- [x] 保存済み Wiki から添付ID・Wiki共有ファイルIDと画像参照の定義有無を確認した。5つの参照ラベルはどちらの添付一覧にもなく、対応する Markdown 参照定義もなかった。
- [x] 5つの各参照IDへ Runtime の `download_wiki_attachment` を1回ずつ直列に実行した。すべて HTTP 404・`UPSTREAM_ERROR` だった。追加の自動再試行はしていない。
- [x] Runtime 内のメソッドが公式仕様と同じ GET パスを使うことを確認した。
- [x] 公式 REST URL を Node の直接接続でも確認しようとしたが接続タイムアウトとなり、状態コードを得られなかった。このため、独立した HTTP クライアントとのステータス比較は未完了として記録する。
- [x] すべての本体取得が404となり、ストリーム・ファイル名・画像形式は得られなかった。認証情報や応答本文は出力・保存していない。
- [x] P0 は現状の参照について回復実装へ進まない判定となった。404だけから削除済みとは結論しない。

今回のP0では Runtime が公式仕様どおりの添付 GET 経路で404を受けた。独立した REST 接続はタイムアウトしたため、HTTP 状態を完全には独立比較できていない。Nulab の Wiki 取得応答には共有ファイル一覧を含められ、保存済み対象データでも確認したが、値は0件だった。現時点で miku-backlog-api や archive に回復処理を追加する根拠はない。画像を回復するには、まず5つの数値ラベルが有効な Wiki 添付IDなのか、または元の画像 URL を指す参照ラベルなのかを確認する。

## P1：取得候補を抽出する

対象コード：`src/archive/collector.mjs` の `unresolvedWikiAttachmentReferences` と `src/archive/render.mjs` の本文解析・添付参照解決。

- [ ] Wiki 本文の画像・添付参照抽出を共通化し、収集と表示で同じ参照を認識する。
- [ ] `#image(ID)`、`#thumbnail(ID)`、`#attach(名前:ID)`、`![代替文][ID]` の未解決な正の安全な整数IDだけを直接取得候補にする。ファイル名からIDを推測しない。
- [ ] 通常の Markdown 参照定義がある場合は、そのラベルを Backlog の添付IDと誤認しない。コードフェンス・インラインコード・エスケープされた記法は取得候補から除外し、表示側の扱いとも一致させる。
- [ ] `(wikiId, attachmentId)` で重複を除く。同じIDへの複数の本文参照は、保存した一つの資産を共有する。
- [ ] Wiki 本体・添付一覧・保存済み補完記録で解決できる参照を先に除外し、不要なダウンロードを発生させない。

## P2：補完資産と取得結果を保存する

対象コード：`src/archive/collector.mjs` の `collectWikiAttachmentList`、`collectWikiAttachments`、`collectAsset`、`recordAsset` と `src/archive/atomic-write.mjs`。

API が返した `wiki.attachments` へ架空の一覧項目を追加せず、補完結果を別の記録として持つ。以下を保存形式の第一候補とする。

| 保存場所 | 内容 |
| --- | --- |
| `data/wiki-attachment-references/<wikiId>.json` | Wiki・プロジェクトID、参照IDごとの取得結果、取得日時、成功時の名前・サイズ・画像形式・ローカルパス、失敗時の安全な理由・HTTP状態 |
| `data/assets/index.json` の `wikiAttachments` | 成功した補完資産を既存資産と同じキーで登録。取得元を区別する任意の `source: "body-reference"` を追加 |
| `assets/wikis/<wikiId>/` | ストリーム取得した本体。Wiki ID と添付IDで一意になる安全な保存名 |

- [ ] 新しい補完記録は `schemaVersion: 1` とし、存在しない旧アーカイブでは空として扱う。既存の保存形式との互換性を維持し、API一覧由来の資産では `source` 省略を許容する。
- [ ] 本体を全量メモリへ保持しない。先頭の限定したバイト列で形式を判定する場合も、確認したバイト列を保存ストリームへ戻し、一度の GET で保存する。
- [ ] Runtime が返すファイル名を利用できれば安全化して使用する。名前が得られない場合は添付IDと検出した形式から補完名を作る。本文の `image` という文言や拡張子だけで画像と判断しない。
- [ ] PNG、JPEG、GIF、WebP、BMP、AVIF の対応を既存の画像表示方針と照合する。形式不明・HTML・SVGは画像として自動表示せず、正常に取得できた本体はダウンロードリンクとして扱う。
- [ ] サイズは実際の保存バイト数を記録する。API が返していない名前・サイズ・作成者・作成日時をAPI由来の値として捏造しない。
- [ ] 一時ファイルからの確定、補完記録、資産索引、進捗完了の順に保存する。途中で停止しても、部分ファイルを完成済み資産として表示しない。

## P3：既存アーカイブの再開と失敗処理

- [ ] 完了済みの `wiki-attachment-list:<wikiId>` とは別に、`wiki-attachment-reference:v1:<wikiId>:<attachmentId>` の進捗を持つ。既存の完了タスクを削除しなくても補完処理へ進める。
- [ ] 保存済み Wiki 本文を読み直して補完候補を算出する。旧アーカイブで `collect` を再開しても、Wiki 本体・一覧・通常添付を再取得せず、新しい候補だけを処理する。
- [ ] 取得成功の補完記録と本体が存在すれば API を呼ばず、資産索引・進捗だけを修復できるようにする。本体が欠落した場合は取得を再開する。メタデータのない孤立ファイルを成功と推測しない。
- [ ] 404・403は「参照先なし／アクセス不可」の解決結果として保存し、参照ごとの警告を出す。通常の再開では同じ取得不能候補を繰り返さない。既存の通常添付ダウンロードの失敗処理は維持する。
- [ ] 取得不能結果を明示的に再確認する必要が生じた場合のために、対象 Wiki・添付IDだけの再試行方法を設計する。全進捗削除を利用者の操作手順にしない。新規アーカイブでは再確認する。
- [ ] 401は認証問題として扱い、候補ごとに連発せず収集を止める。429は共有スケジューラの待機・停止・再開を使用する。408・5xx・通信失敗は既存の上限付き再試行、ストリーム途中の失敗は未完了扱いとする。
- [ ] 補完候補の404・403は未解決参照の警告とし、正常に取得済みの本文を閲覧できる状態を保つ。一時的な取得失敗や認証・レート制限停止は収集の未完了状態へ反映する。

## P4：ローカル表示と収集状況

対象コード：`src/archive/render.mjs` の `attachmentReferenceMap`、Wiki 詳細表示と `src/archive/report.mjs`。

- [ ] Wiki API由来の添付と、取得に成功した補完資産を合わせて参照を解決する。同じIDでは既存の添付メタデータを優先し、リンクを重複させない。
- [ ] `![image][1074278457]` などの本文参照を、確認済みの画像形式なら保存済みローカル画像へ置き換える。画像以外は添付リンクとして表示する。
- [ ] 解決できない参照は元の参照を保持し、未解決・アクセス不可などを表示する。添付一覧にないことと、本体の取得失敗を区別する。
- [ ] 収集状況に補完候補数・取得済み数・取得不能数・一時失敗数を表示する。HTTP 状態だけで判断できない理由は「不明」とし、本文や認証情報を表示しない。
- [ ] 旧アーカイブは補完記録なしで描画できること、`file://` 表示で外部通信を発生させないことを確認する。

## P5：検証と文書更新

- [ ] Collector：一覧が空でも本体 GET が成功する模擬例、複数参照の重複排除、既存添付の再利用、数値以外・コード・Markdown参照定義の除外を検証する。
- [ ] Collector：404・403の警告と再開時の省略、401停止、429待機と上限停止、ストリーム途中失敗、保存途中の各段階からの再開を検証する。
- [ ] Renderer／Report：一覧にない保存済み画像の参照解決、未知形式のリンク表示、未解決参照の表示、旧形式の互換性と外部 `src` 不在を検証する。
- [ ] 別の有効な参照IDで P0 の本体取得成功が確認された場合に限り、対象アーカイブをバックアップして少数候補から再開する。同じ本文IDへの GET は一度に抑え、既存資産を再取得しないことを確認する。
- [ ] `runtime verify`、構文チェック、関連テスト、`verify`・`report`・`render` を実行する。実 API 検証の成否と制約を記録する。
- [ ] `docs/inline-images.md`、`docs/archive-format.md`、`docs/backlog-api-integration.md` と README を実装に合わせて更新する。「添付一覧に対応付く画像だけ」という現在の方針へ、同じ Wiki の本体 API で取得に成功した本文参照を追加する。

## 完了条件

実 API で本体取得が成功した参照は、一覧に項目がなくても一度だけ保存でき、本文と添付表示からオフラインで閲覧できる。再開時は保存済み成功・取得不能結果を再利用し、旧アーカイブの通常資産を再取得しない。取得不能な参照には理由区分が残り、レート制限と取得範囲を維持する。

今回の5参照は未回復である。参照定義または現在有効な添付ID／URLが確認できるまでは、回復できることを前提とした実装へ進まない。別の有効な本文参照で本体 GET の成功が確認できた場合は、この計画の P1～P5 を再開する。
