作成日・実装完了日：2026-09-30。進捗と完了結果は [TODO.md](../TODO.md) にも記録する。

当初は計画のみの依頼だったが、その後ユーザーから実装開始の指示を受けた。P1 → P2 → P3 → P4 → P5 の順に実行し、オフライン検証と実 Backlog 確認まで完了した。各段階の実装と確認内容を以下に記録する。

## 目的と境界

- Backlog の制限に合わせて待ち、429の連続発生を抑える。
- 保存項目を減らさず、課題一覧で得られる本体の個別再取得を省く。
- 既存の途中アーカイブを再開し、完了済み課題と資産を再利用する。
- 通信は固定済み `miku-backlog-api` v0.7.10 Runtime の `runOperation` と `openDownload` を使い、権限は `READ` とする。
- レート管理と取得手順の責務は archive のコアに置く。CLI は待機通知の表示だけを担当する。
- 完成済みの `data/`・`assets/` と既存 CLI コマンドの形式を維持する。補助的な取得状態は `state/` に置く。
- コメント・参加者・関連課題・Wiki 本文・ファイル本体は現在の保存範囲を維持する。差分同期、並列取得、APIキー切り替え、依存 Runtime の更新は今回の対象に追加しない。

同じユーザーの別アプリも制限枠を消費するため、429が一切発生しないことは保証しない。429になっても適切に待機し、上限に達したら再開可能な状態で終了できることを完了条件とする。

## Runtime の契約：取り違えないこと

Runtime のアクセスイベントは `phase: 'success' | 'failure'` に以下の任意メタデータを持つ。

```text
rateLimit.limit      非負の整数（使用する場合は正の値であることを検査）
rateLimit.remaining  非負の整数
rateLimit.resetAt    ISO 8601 の日時文字列
httpStatus           HTTP状態
```

Backlog の生ヘッダー `X-RateLimit-Reset` はUNIX秒だが、Runtime はISO日時へ変換済みである。archive 側は `Date.parse(resetAt)` で扱い、再度1000倍しない。任意フィールドの欠落、不正な日時、不正な数値を処理できるようにする。

契約を再確認する際は固定 Runtime または、存在する場合に限り `workplace/miku-backlog-api/src/core/contracts.ts`・`backlog-access-context.ts`・`verbose-client.ts`・`download-operation.ts` を参照する。`workplace/` の上流ソースを本製品の依存や編集対象にしない。

## P1：共通のレート管理

変更の中心は `collector.mjs`。計算と時刻管理は必要に応じて `src/archive/rate-limit.mjs` に分け、その場合は `package.json` の `check` 対象に加える。

1. `collectArchive` の実行ごとに、通常呼び出しとダウンロードが共有する管理状態を生成する。別アーカイブや次回実行へメモリ状態を無条件に持ち越さない。
2. `get_issues`・`get_wiki_pages` を `search`、現在使用するその他のGET操作と三種のダウンロードを `read` に分類する。`READ` 権限とレート種別は別概念であり、権限から種別を決めない。
3. `callOnce` と `openDownloadOnce` の送信直前に、該当枠の次回送信可能時刻を確認する。全アクセスを引き続き直列にする。
4. 成功／失敗イベントのレート情報を検査し、該当枠の状態を更新する。通常APIもダウンロードも同じ経路で処理する。
5. 待機計算は以下の初期方針を使う。定数を一か所へまとめ、CLIの新しい調整オプションは追加しない。

| 条件 | 次のリクエストまでの方針 |
| --- | --- |
| 正の `limit` がある | 基本間隔を `ceil(60_000 / (limit * 0.8))` ミリ秒とする。上限の80%を目安に余裕を取る |
| `limit` がない／不正 | 基本間隔は1,000ミリ秒。初回は保存済み待機状態がなければ送信可能 |
| `search` | 基本間隔を最低1,000ミリ秒とする |
| 有効な未来の `resetAt` と `remaining > 1` | 基本間隔と `ceil((resetAtMs - nowMs) / (remaining - 1))` の大きい方を使い、残枠を時間に分散する |
| `remaining <= 1` | 有効な未来の `resetAt` ＋1,000ミリ秒まで待つ。リセット情報がなければ60,000ミリ秒待つ |
| リセット時刻を過ぎた状態 | 古い残数は失効させる。次の応答で更新する。残数ゼロを永久に使い続けない |

この間隔は最後のアクセスの終了を基準にする。再試行待機と通常ペース調整を単純に足さず、両方を満たす最も遅い送信可能時刻まで待つ。

時刻と待機を注入できる構造にする。既存の `now`・`wait` を利用し、テストの `wait` は仮想時刻も進める。時刻固定のまま待機判定を繰り返して無限ループにしない。

完了条件：成功応答だけでも残数に合わせて待つ。検索と読み込みの状態が混ざらない。ダウンロードの429にも同じ仕組みが適用される。

## P2：429の再試行と収集全体の終了

1. `OperationFailure` に検査済みレート情報を伝える。HTTP状態、操作名、安全な対象ID、試行回数の既存記録は維持する。
2. 429では、有効な未来の `resetAt` ＋1,000ミリ秒まで待つ。日時が欠落、不正、過去の場合は60,000ミリ秒待つ。
3. 408・5xx・HTTP状態が不明な一時的上流エラーは既存の1秒・2秒バックオフを維持する。429を通常バックオフへ流さない。
4. リクエスト試行の上限は初回を含め3回とする。3回目の429では追加リクエストを送らず、収集終了を示す専用のエラー種別またはフラグを返す。
5. すべての取得タスクの `catch` を点検する。`collectIssue`、`collectWiki`、`collectAsset` などの「失敗を保存して false を返す」処理は、429上限到達時だけ再送出する。一覧・共有ディレクトリの経路も確認する。通常の個別失敗は既存の挙動を維持する。
6. 外側の `collectArchive` で `manifest.collection.status`・`progress.phase` を `incomplete` に確定する。原因タスクの失敗は一度だけ記録し、未着手タスクを大量に失敗扱いしない。HTTP429の記録をローカルエラーで上書きしない。
7. 上限到達時にも次回送信可能時刻を保存する。次回 `collect` は、プロジェクト解決を含む最初のAPIより前に、該当枠に残る待機を守る。

長い待機の開始前に `progress.json` を原子的に保存する。v1に任意の `rateLimit`（枠ごとの検査済み情報と `blockedUntil`）および `waiting`（枠・理由・開始時刻・再開予定時刻）を追加する方針とする。現在の `phase` やタスク状態へ新しい必須列挙値を導入しない。旧progressでフィールドがない場合も読めること。不正な任意値をそのまま待機や表示へ使わない。

待機終了時に `waiting` を消す。上限到達による終了時も「実行中の待機」は消し、次回用の `blockedUntil` は残す。`format.mjs` の任意項目の検証と `docs/archive-format.md` に仕様を追加する。

完了条件：3回の429の後は、別課題・Wiki・ファイルへのAPIが一度も呼ばれない。保存された進捗は `verify` 可能で、再実行すれば待機後に失敗タスクから取得できる。

## P3：課題一覧の本体再利用

### P3a：保存内容の同等性を確認する

`normalizeIssue` の出力項目すべてについて、「一覧にあるか」「個別詳細との差」「欠落時にどう補完するか」を表にして、この文書または `docs/issue-data.md` に根拠を記録する。

特に本文、カスタム属性、親課題ID、添付情報の作成者・日時、共有ファイル情報を点検する。公式のレスポンス例だけで完全な同等性を断定しない。既存テストの一覧fixtureは要約だけなので、APIの実際の完全性の証拠にしない。

まず仕様と既存のローカル資料を比較し、実装後のP5の少数件確認で一覧／詳細の正規化結果を照合する。比較用の生レスポンスや個人情報を追跡対象ファイルに残さない。欠落・null・空配列を区別し、正規化で欠落が空配列へ変わっただけのデータを「完全」と認定しない。

同等性を確認できた場合だけ本体再利用を有効にする。情報が不足する課題は `get_issue` で補完する。必要な保存項目を得るため上流Runtimeの新操作が必要と判明した場合、その不足を記録し、P3の最適化を完了扱いしない。Runtimeを独断で更新せず、P1・P2の改善は独立して完了できるようにする。

2026-09-30 の少数件実API確認では、MIGTEST01 の一覧／詳細3件を `normalizeIssue` 後に比較し、3件すべての必須項目が揃い、保存対象の差分はなかった。比較した課題IDは `36038336`、`36038330`、`36038314`。生レスポンスは保存していない。この少数確認は、全課題の一律同等性を保証するものではないため、実装は項目・配列・添付・共有ファイルの存在を個別に検査し、不足分を `get_issue` へ戻す。

### P3b：正規化済み本体を中断可能な形で保存する

保存先は `state/issue-details/<issue-id>.json`。次の情報だけを持つ補助ファイルとする。

```text
schemaVersion: miku-backlog-archive/issue-detail-cache/v1
archiveId: このアーカイブのID
projectId: このアーカイブのプロジェクトID
savedAt: 保存日時
source: issue-list または issue-detail
issue: normalizeIssue 済みの本体
```

再利用可否を示す条件はP3aの表から定義し、記録方法を文書化する。生レスポンスや認証・不要な人物情報は保存しない。読込時はschema、archiveId、projectId、issue.idを照合する。

1. `collectIssueIndex` で、各ページの正規化済み本体キャッシュ → 要約index → `nextOffset` の順に原子的に保存する。
2. ページの全キャッシュが確定するまではoffsetを進めない。途中で落ちたページは再取得してID単位で統合する。
3. `collectIssue` は、完了済み課題ならまず既存のスキップを適用し、未完了で有効かつ十分なキャッシュがあればそこから本体を読む。
4. その後コメント・参加者・関連課題を取得し、既存形式の `data/issues/<id>.json` を確定してからタスクを完了にする。キャッシュだけで課題全体を完了扱いしない。
5. キャッシュがない／不足する旧アーカイブは `get_issue` を使う。個別取得の正規化済み本体もキャッシュしてからコメント等を取得し、後段失敗の再開で本体を再取得しない。
6. キャッシュの破損・識別不一致を検出した場合はローカルデータの不整合として停止する。別アーカイブのキャッシュを混ぜず、黙って上書きもしない。欠落は旧アーカイブ互換として扱う。

今回の途中アーカイブは一覧の本体をすでに捨てているため、過去のレスポンスをローカルから復元できない。最初の改善では旧アーカイブの不足分を個別取得する方針に固定する。一覧を全部再取得する移行処理は加えず、レート管理で安全に再開する。

完了条件：十分な一覧データを持つ新規収集では `get_issue` が0回。旧アーカイブも再開でき、後段失敗で保存済み本体を再取得しない。最終的な保存内容が従来と同等である。390回の削減は全390課題が再利用条件を満たす新規収集の場合の上限であり、今回の途中取得への削減保証ではない。

## P4：待機通知と仕様文書

- コアの任意の `onProgress` コールバックで、待機の開始／終了、枠、理由、再開予定時刻を通知する。生レスポンスや環境変数は渡さない。
- CLIはその通知から「レート制限のため待機中」「再開予定時刻」を標準エラーへ表示する。毎秒のカウントダウンや大量の短時間待機ログは追加しない。表示対象は429待機と5秒以上のペース調整を目安にする。
- `report` は検査済みの `progress.waiting` と次回用の待機期限だけを追加表示する。通常の失敗表、許可項目、HTMLエスケープを維持する。レポートは生成時点の状態であり、自動更新ではないことを示す。
- 完了・通常処理復帰・収集終了時に実行中の待機表示が残らないことを確認する。
- `README.md`、`docs/backlog-api-integration.md`、`docs/archive-format.md`、必要に応じて `docs/issue-data.md` を実装後の実際の仕様へ更新する。現在の1秒・2秒という説明は429と通常一時失敗を分けて記載する。

完了条件：待機中と単なる失敗を判別でき、旧progressでもCLIとreportが正常に動く。

## P5：検証と実Backlogでの再開

### オフラインで行う検証

既存 `fixtureRuntime` を必要最小限拡張し、success／failure双方で任意の `rateLimit` を渡せるようにする。仮想時刻と待機記録を使い、実時間で60秒待つテストは作らない。429の旧テストは新仕様へ更新し、5xxの1秒・2秒待機は別のテストとして残す。

- [x] `resetAt` のISO日時が正しく解釈され、リセット＋1秒まで待つ。
- [x] 429のヘッダー欠落・不正・過去日時で60秒待つ。
- [x] 通常成功の残数ゼロ／1で待ち、リセット後は古い残数を失効する。
- [x] 検索の待機が読み込み枠を書き換えない。GETとダウンロードは同じ読み込み枠を共有する。
- [x] GETおよびダウンロード開始の429が3回続くと収集全体が終了し、後続対象は呼ばれない。
- [x] 次回実行では保存された待機期限より前にAPIを呼ばず、期限切れの保存済み待機では長時間待たない。
- [x] 404個別失敗、5xxバックオフ、ストリーム途中失敗で不完全ファイルを確定しない。
- [x] 完全な一覧fixtureでは `get_issue` が0回、要約だけのfixtureとキャッシュなしの旧アーカイブでは補完される。
- [x] 孤立した課題詳細キャッシュがあっても最初の一覧ページを取得する。ページ途中失敗後は保存済みoffsetから再開し、indexとoffsetの更新間で重複してもIDで統合して飛ばさない。
- [x] キャッシュ保存後に参加者取得等が失敗しても、再開時に課題本体を取得し直さない。
- [x] キャッシュの破損／他archiveId／他projectIdを検出し、完成済み課題を上書きしない。
- [x] 一覧再利用と個別詳細経路の正規化済み課題本体を比較し、添付・カスタム属性等が同じである。
- [x] テストではキャッシュと進捗に渡したAPIキーが保存されないこと、不要なメール情報を除去すること、レポートが許可フィールドだけを出してHTMLをエスケープすることを確認した。CLIは待機の安全なメタデータだけを表示する。

- 実API再開で共有ファイルのルート `/` が `illegal path` を返すことを確認し、API送信時に限って `./` へ変換する修正を加えた。ローカルのルート表現 `/` は維持する。
- 完了済みデータ、認証情報、依存Runtime、取得範囲を不用意に変更していない。
- 実 API 確認と途中アーカイブの再開を実施し、件数と完了状態を上記に記録した。
- `git diff` と `git status --short` で対象外の変更を点検する。計画作成時点で `.gitignore` に既存の変更があるため、実装担当の変更と混同しない。
