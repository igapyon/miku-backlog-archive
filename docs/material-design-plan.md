# Material Design 3 導入の設計・計画

作成・更新日：2026-10-01。採用方針：セマンティックな HTML と CSS を基本にする。状態：画面コード、自己レビューで見つかったナビゲーション2件、Wiki本文解析の不具合2件を実装済み。利用者による表示確認と自動回帰確認は実施済み。個別のブラウザー・アクセシビリティ受け入れ確認は TODO に残す。Wiki本文解析の修正内容と検査結果は[Wikiページ名リンク対応計画の第7節](wiki-page-links-plan.md#7-自己レビューで見つかった本文解析2件の修正計画)に記録する。

## 1. 目的と導入範囲

保存したプロジェクトを後から読み返すため、課題の本文と経緯、Wiki、ファイルの所在を読みやすくする。セマンティックな HTML を出力し、Material Design 3（以下 MD3）を参照した色・文字・余白・形状・状態表示を共通 CSS で全ページに適用する。

MD3 はデザインの指針として採用する。初回の UI は標準 HTML 要素と CSS カスタムプロパティで実装し、Material Web（`@material/web`）などの UI ライブラリや UI ビルド用の依存を導入しない。ブラウザーの標準操作を活かし、必要な表示と操作を製品側の小さな CSS で整える。

初回の対象はホーム、課題一覧・詳細、Wiki 一覧・詳細、共有ファイル一覧、収集状況レポート。ライト／ダーク表示、狭い画面への対応、キーボード操作、印刷用 CSS も含める。基本の本文・一覧・ページ移動・添付リンクは静的 HTML で成立させる。

検索・絞り込み・並び替えは後続の機能として判断する。初回は一覧の全件表示とブラウザー内検索を使い、独自の検索索引や仮想スクロールを加えない。本文記法の完全互換、取得範囲の拡張、Backlog への更新機能はこの導入範囲に含めない。

| 現在の入口 | 現状 | 導入時の対応 |
| --- | --- | --- |

この文書は修正や実 API 収集を実行する指示書ではなく、UI 導入の作業順と判断条件を定める。

## 3. セマンティックな HTML と CSS による実装方式

### 3.1 採用案

ページの構造・情報・操作を標準 HTML 要素で表し、MD3 の役割別トークンを CSS カスタムプロパティとして定義する。共通 CSS は `render`・`report` の生成時に `site/assets/style.css` へ配備し、各ページから相対パスで読み込む。

初回の閲覧画面は JavaScript を要求しない。OS に応じたライト／ダーク表示は CSS の `prefers-color-scheme`、補助情報の開閉は `details`／`summary`、ページ移動は `a` で成立させる。カスタム要素の登録や、表示後の DOM の置き換えを基本操作の前提にしない。

本計画でいう MD3 対応は、共通トークンと画面設計を MD3 に沿って整えることを指す。全コンポーネントの仕様を独自に再実装することや、公式部品との完全な一致を完了条件にしない。

### 3.2 HTML 要素と操作の設計

| 情報・操作 | HTML と表示方針 |
| --- | --- |
| ページ構造 | `header`、名前付きの `nav`、`main` を使い、ページタイトルは `h1`、各まとまりは順序のある見出しで示す |
| ページ・ファイルへの移動 | `href` のある `a` を使う。主要入口は CSS でボタン風に表示しても、リンクとしての意味と操作を保つ |
| 情報の一覧 | 表形式の情報は `table`、`caption`、`th` と `scope`、項目の列挙は `ul`／`ol` を使う |
| 属性・メタ情報 | 名前と値の対応は `dl`／`dt`／`dd` で表す |
| 日時 | 有効な日時は `time` と機械可読な `datetime` で表し、表示文字列は既存の JST 形式を保つ |
| 補助情報の開閉 | `details`／`summary` を使う。重要な本文・コメントは初期表示する |
| 状態・優先度・タグ | 非操作の文字ラベルとして表示し、色を補助として使う |
| 将来の操作・入力 | 実際の処理には `button`、入力には `label` と標準フォーム要素を使う。新しい機能を導入する段階で操作と必要な JavaScript を設計する |

`div` や `span` にクリック処理・タブ操作を足してリンクやボタンを再現しない。HTML 標準の意味とキーボード操作を活かし、ARIA は現在地や領域名など、標準要素だけでは足りない情報に限定する。

### 3.3 CSS とローカル資産の配備

- `src/ui/` にトークンと共通 CSS のソースを Git 管理する。既存の Node.js の機能で、トークン → 共通スタイルの順に読み込み、一つの `style.css` として原子的に書き込む。
- CSS の前処理・圧縮・JavaScript バンドルを初回の工程に加えない。従来の `node src/cli.mjs ...` から生成・再生成できる構成にする。
- `render` と独立した `report` が同じ配備処理を使う。CSS の不足は生成前に検出し、CSS 内の外部 `@import`、外部 URL、フォント取得を加えない。
- 第三者 SVG を採用する場合は、固定リビジョン・出典・ライセンスをソース側に記録し、必要な通知をアーカイブに同梱する。表示用アイコンは信頼済み SVG を生成時にインライン化する。
- 基本の閲覧・移動・ファイル参照は JavaScript 無効でも成立させる。CSS を読み込めない場合も、HTML の順序とラベルで内容を読み取れる構造にする。

### 3.4 UI ライブラリを再検討する条件

標準要素と CSS で扱えない複雑な操作が必要になった場合に、UI ライブラリの採用を別途検討する。対象部品、アクセシビリティ、`file://`・オフライン動作、依存と保守負担、版・出典・ライセンスを比較する。

今回の MD3 導入は、HTML・CSS による画面整備と本計画の受け入れ条件で完了を判定する。ライブラリの選定・導入を後続工程の前提にしない。

## 4. 見た目の設計

### 4.1 色・文字・形状の共通トークン

落ち着いた青緑を基調とする。基準色の案は `#006A60`。本文領域は彩度を抑え、強調色をナビゲーションの選択状態と主要リンクに使う。基準色からライト／ダークの役割別パレットを作り、P1 でコントラストを検証して具体値を固定する。下表の数値は本製品の初期設計値であり、部品すべてに強制する値ではない。

| 項目 | 初期設計 |
| --- | --- |
| 色の役割 | `--md-sys-color-primary`／`on-primary`、`primary-container`／`on-primary-container`、`secondary` と対応する container・on 色、`surface`／`on-surface`、`surface-container-*`、`on-surface-variant`、`outline`／`outline-variant`、`error` と対応する container・on 色 |
| テーマ | OS の `prefers-color-scheme` に合わせたライト／ダーク。手動切替と設定保存は初回に加えない |
| 日本語フォント | `system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", "Hiragino Sans", "Yu Gothic", Meiryo, sans-serif`。OS のフォントを使い、外部配信や追加フォントファイルを要求しない |
| ページタイトル | 28px／行高36px。長い題名は折り返す |
| セクション見出し | 22px／行高28px |
| 本文 | 16px／行高28px。長文の幅は最大48remを目安にする |
| メタ情報・一覧 | 14px／行高20〜24px。重要な値を過度に小さくしない |
| 操作ラベル | 14px／行高20px、medium 相当 |
| 余白 | 4pxを基準に8／12／16／24／32px。本文のまとまりごとに24〜32px |
| 形状 | 内容パネル12px、概要カード16px。主ナビの選択状態とボタンは丸みのある形状 |
| 高さ・影 | 内容は平面を基本にし、面の色・境界線で区切る。長い本文や各コメントに大きな影を付けない |
| 動き | ホバー・フォーカスの短い状態変化だけ。`prefers-reduced-motion` に対応する |

トークンを本文、ナビゲーション、ボタン風リンク、表、バッジなど全画面の CSS で共有する。役割別の色や文字の値は `--md-sys-*`、製品固有のレイアウト値は `--archive-*` として定義し、部品ごとに色や寸法を重複して直書きしない。ホバー、`:focus-visible`、押下、現在地の状態も共通 CSS で整える。

課題の状態と優先度は文字ラベルとして表示する。状態を色分けする場合も、値を検証した上でラベルの背景色にだけ使い、本文の文字色へ直接使わない。色だけで状態を伝えず、データの値を CSS や属性へ無検証で挿入しない。

### 4.2 共通レイアウト

広い画面では左に幅240pxのナビゲーション、右に最大幅のある内容領域を置く。全体は最大1440px程度。上部にはプロジェクト名と、閲覧ページが保存時点の内容であることが分かる取得完了日時を表示する。本文のページタイトルは `main` 内に置く。

```text
┌─────────────────────────────────────────────────────────┐
│ プロジェクト名                         保存日時         │
├────────────┬────────────────────────────────────────────┤
│ ホーム     │ ページタイトル                             │
│ 課題       │                                            │
│ Wiki       │ 概要・本文・一覧など                        │
│ ファイル   │                                            │
│ 収集状況   │                                            │
└────────────┴────────────────────────────────────────────┘
```

| 画面幅 | 配置 |
| --- | --- |
| 1200px以上 | 左ナビ＋内容。課題詳細は本文と属性欄の2列を使える |
| 600〜1199px | 上部の横並びナビ＋内容1列。リンクは必要に応じて折り返す |
| 600px未満 | 上部の折り返すナビ＋内容1列。左右余白16px。題名・日時・ファイル名を折り返す |

ナビゲーションはリンクのリストとし、リンク先が現在のページなら `aria-current="page"`、詳細ページで所属する一覧を示すなら `aria-current="location"` を使う。ページ移動のナビに ARIA のタブ操作を持ち込まない。先頭に「本文へ移動」のリンクを置く。表は意味のある `table` のまま、狭い画面では名前付きの横スクロール領域に収める。本文全体の横スクロールは発生させない。

固定ヘッダーを使う場合は、コメントアンカーやフォーカス位置が隠れないように `scroll-margin-top` などを設定する。印刷時はナビと操作部品を外し、本文・属性・変更記録を読み取れる表示にする。

### 4.3 アイコン

初回のナビゲーションと入口は文字ラベルを使い、アイコン資産を追加しない。後からアイコンを加える場合は、ローカル SVG を同梱し、外部配信のフォントや画像を閲覧時に読み込まない。

## 5. ページ別の設計

| ページ | 情報の並び・表示 | 部品と注意点 |
| --- | --- | --- |
| ホーム | プロジェクト名・説明、課題／Wiki／共有ファイル件数の概要カード、取得元・開始／完了日時・保存ファイル総数 | 件数カードは見出しとテキストで構成する。各一覧への入口は `a` を CSS で tonal ボタン風に表示する |
| 課題一覧 | 件数、キー・件名・状態・担当者・更新日時の表 | 状態は文字付きバッジ。件名を折り返し、キーを判別しやすくする。全件を HTML に残す |
| 課題詳細 | キー・件名・状態、説明、コメントの経緯。属性は横または上にまとめ、添付・共有ファイル・親子／関連課題・参加者・カスタム項目を独立したまとまりで配置 | 日付・工数・分類・作成更新情報を省略しない。コメントの `#comment-ID` を維持する。補助情報は `details` を使えるが、本文・コメント内容は初期表示する |
| Wiki 一覧 | 件数、題名・タグ・更新日時の表 | オブジェクト形式と旧文字列形式のタグ表示を扱う。タグは非操作のラベルとして表示する |
| Wiki 詳細 | 題名・タグ・作成／更新情報、本文、添付・共有ファイル | 本文幅を制限し、見出し・引用・コード・画像を共通 CSS で整える |
| 共有ファイル | ルートへの入口、フォルダ階層とファイル名・サイズ | 現在の階層・フォルダアンカーを保つ。通常のリンクと必要に応じた `details` で辿れる構成にする |
| 収集状況 | 収集状態・更新時刻・待機予定・失敗件数の概要、失敗タスク表 | 未完了時も単独で使える。「生成時点の状態」を表示し、動く進捗バーや自動更新を付けない |

添付一覧はファイル名・サイズ・取得済み画像のプレビューを並べる。表示用の名前とエンコードした参照 URL を区別する。本文の既存内部リンク、外部リンクの条件、画像の取得対象、安全な HTML 化の条件は、見た目の変更後も検証対象とする。

収集状況の色は、完了＝通常の強調、不完全／失敗＝error、待機＝中立の情報表示とする。状態を日本語で表示する場合も、操作名・HTTP・再試行可否・API試行回数・記録日時の情報を保つ。

### 収集状況とメニューの生成順

完成したサイトには収集状況も含めるため、`renderArchive` の最後にレポートを生成する。ホーム・各一覧・各詳細には収集状況への相対リンクを出力し、`render` が正常終了した時点でリンク先が存在するようにする。依存は `render` → `report` → `ui` と `render` → `ui` にし、レポートから本文生成器へ依存しない。この連携は実装済みで、第10節に実装と確認結果を記録する。

独立した `report` 実行でも、共通 CSS と採用した第三者資産の通知を配備する。収集未完了の場合や本文サイトをまだ生成していない場合は、存在しないページへのメニューを出さない。完成済みの manifest と対象 HTML の存在を確認できるリンクだけを出す。ヘッダーのプロジェクト名にも同じホームの有無の判定を使い、ホームがない場合は通常の文字として表示する。`render` と `report` のどちらから先に実行しても、共通資産を壊さない。

## 6. 実装ファイルとアーカイブへの配備

以下は新設先の案。詳細は P0 で固定する。

```text
src/ui/
  page.mjs                 共通レイアウトとナビゲーション
  assets.mjs               CSS ソースの読み込み・結合・原子的な配備
  tokens.css               ライト／ダークの MD3 トークン
  archive.css              レイアウト・本文・表・印刷の CSS

生成先：
site/assets/
  style.css                tokens.css と archive.css を順に結合したもの
```

CSS の現在の参照先 `site/assets/style.css` は継続使用する。HTML と同じ深さ計算に基づいて CSS への相対参照を作る。CSS ソースの不足・読み込み失敗はページ生成前に検出し、配備は既存の原子的書き込みを使う。編集するのは `src/ui/` のソースとし、出力先の `style.css` は `render`／`report` で再生成する。

保存 JSON のスキーマ変更は UI 導入に必要ない。既存の完成済みアーカイブには `render` の再実行で新しい画面を適用できる。レポートだけの場合は `report` を再実行する。以前の生成 HTML を読んで変換する方式にはしない。

API 収集層と表示層の責務を維持し、共通 UI と CSS の配備処理はローカルデータとソース資産だけを扱う。閲覧画面の導入による追加の Backlog API 通信は発生させない。

### 10.2 実装方針と順序

1. **共通ページとメニューを整える。** `src/ui/page.mjs` のメニュー定義に「収集状況」を追加する。ページ枠は渡されたメニューからホームの有無を判断し、ヘッダーのプロジェクト名にもその判断を使う。相対パス・エスケープ・`aria-current` は共通処理で扱う。
2. **単独レポートのリンクを確定する。** `src/archive/report.mjs` では、manifest が完成済みで対象HTMLが存在する場合に本文サイトへのメニューを出す。収集状況自身は常に1項目だけ表示し、`aria-current="page"` を付ける。ホーム未生成時にはヘッダーからもホームへのリンクを出さない。
3. **本文サイトの生成にレポートを含める。** `src/archive/render.mjs` の全ページに収集状況を含むメニューを渡し、本文ページの生成後に `renderCollectionReport` を呼ぶ。レポート生成に失敗した場合は `render` をエラー終了させる。`render` の正常終了時に、本文サイトとレポートの双方向のリンク先がそろうことを完了条件とする。
4. **回帰テストと利用手順を更新する。** `test/render.test.mjs`・`test/report.test.mjs` に下表のケースを追加する。README とアーカイブ形式の資料には、`render` がレポートも生成し、`report` は未完了時の単独生成や進捗の再生成にも使えることを記載する。
5. **取得済みアーカイブへ適用する。** `workplace/test-migtest01-20260930-file-import` に `render` を再実行し、ホーム・各一覧・課題／Wiki詳細・レポート間のリンクを確認する。

生成には保存済み JSON とローカル CSS を使い、Backlog API の呼び出しや再収集を要求しない。従来の v1 アーカイブ、`render` の完了済み条件、`report` の単独実行に対応する。
