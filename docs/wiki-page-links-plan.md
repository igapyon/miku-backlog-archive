作成・更新日：2026-10-01。状態：基本対応と自己レビューで見つかった本文解析の不具合2件を実装・回帰確認済み。取得済みアーカイブを保存済みデータだけで再生成し、全ページのローカル参照を検査した。Backlog API は利用していない。実装手順と結果は第7節に記録する。

## 1. 確認結果

実装前は `[[CodingRule]] : コーディングルールのトップページ` がリンクにならず、二重括弧を含む文字として出力されていた。

初回実装前に `workplace/test-migtest01-20260930-file-import` で以下を確認した。

- Wiki `CodingRule` の本体 JSON と生成先 `site/wikis/2092281.html` は保存済み。対象の欠落が原因ではない。
- `[[CodingRule]]` は11件のWiki本文に各1箇所あり、実装前のHTMLでもすべて文字のまま残っていた。
- 例：実装前の `site/wikis/2092172.html` の本文は `<ul><li>[[CodingRule]] : コーディングルールのトップページ</li></ul>` となっていた。
- 実装前のコードで完成済みの小さな fixture を新しく生成しても、同じ結果になった。生成時の `fetch` 呼び出しは0回だった。
- Wiki本文にある二重括弧の参照は原文で606箇所・61題名。今回確認したデータではすべて保存済みWikiの題名に一意に一致し、79ページの題名に重複はなかった。この件数は原文の出現数であり、コードブロックなどを含めたリンク生成数の完了条件にはしない。

Backlog の[公式Wikiガイド](https://wiki-guide.backlog.com/practice/08/)でも、`[[Wikiのページ名]]` を使ったWikiへのリンクが案内されている。

再現時の原因は `src/archive/render.mjs` の本文変換に、二重括弧からWikiの題名を取り出して解決する処理がなかったこと。既存の内部リンク変換は課題キー、コメントID、Wiki ID付きURLなどを扱う一方、Wikiのページ名は対象外だった。

### 課題の説明・コメントへの適用確認

[公式Wikiガイド](https://wiki-guide.backlog.com/practice/08/)には、課題コメントに `[[Wikiのページ名]]` と書いた場合にもWikiへのリンクに変換されることが明記されている。

生成器の `issuePage` は課題の説明（`issue.description`）と各コメント（`comments[].content`）を、Wiki本文と同じ `renderBody` に渡す。そのため実装前は課題の両方の本文にも同じ未対応があった。

保存済みアーカイブの390課題と3,332コメントを確認した範囲では、説明・コメント内に二重括弧の参照はなかった。実データでの課題側の再現例は得られていないため、以下のローカル fixture を使って確認した。

- 保存済みWiki `CodingRule`（ID `2092281`）と、説明に `説明 [[CodingRule]]`、コメントに `コメント [[CodingRule]]` を持つ完成済み課題を用意した。
- 実装前の生成器で新しくHTMLを作成すると、説明・コメントの両方で `[[CodingRule]]` が文字のまま残った。期待する `../wikis/2092281.html` へのリンクは0件だった。
- コメント自身の `id="comment-501"` は維持され、生成時の `fetch` 呼び出しは0回だった。

課題の説明と全コメントを、今回のWikiページ名リンク対応の対象に含める。両フィールドの確認を回帰テストでそれぞれ実施する。

## 2. 修正後の挙動

Wiki本文、課題の説明、課題の全コメント、ホームのプロジェクト説明にある `[[Wikiページ名]]` を、同じアーカイブ内の保存済みWikiに対応する相対HTMLリンクへ変換する。

Wikiページからの例：

```html
<a href="2092281.html">CodingRule</a> : コーディングルールのトップページ
```

二重括弧はリンクの表示名に含めず、後ろの ` : コーディングルールのトップページ` はそのまま残す。

| 生成元 | `CodingRule` へのリンク先 |
| --- | --- |
| ホームのプロジェクト説明 | `wikis/2092281.html` |
| 課題の説明（`issue.description`） | `../wikis/2092281.html` |
| 課題の各コメント（`comments[].content`） | `../wikis/2092281.html` |
| Wiki本文 | `2092281.html` |

段落、生成器が対応済みの見出し・箇条書き・引用にも共通の本文変換を適用する。

課題側の例：

```html
<a href="../wikis/2092281.html">CodingRule</a>
```

## 3. 解決と安全な出力の条件

- 全件のWiki本文を読み込んだ後、実際に保存されている `wiki.name` と正のWiki IDから名前の索引を作る。題名は完全一致で照合し、日本語・空白・階層名の `/` なども保存された題名の一部として扱う。
- 同じ題名に対応するIDが1つの場合だけリンクにする。重複した題名、未収集のページ、空の参照、閉じていない括弧などは文字として保持する。
- 大文字小文字の変換、Unicode正規化、URLデコード、末尾の階層名だけによる一致や曖昧検索でリンク先を推測しない。
- リンク先には保存済みのWiki IDを使う。題名からファイルパスやBacklog URLを作らない。表示名と周囲の本文は既存のHTMLエスケープを使う。
- Wiki参照を一つのトークンとして扱い、題名の一部を課題キー・画像マクロなどとして再変換しない。生成したリンクをさらに解析してリンクを入れ子にしない。
- 課題キー・URLとして認識される二重括弧の内容は既存の扱いを優先する。今回追加するのはWikiのページ名だけで、二重括弧のURLや表示名指定をWiki名として推測しない。
- 現在対応しているMarkdownのコードブロック内はリンク化しない。Backlogのコードマクロや詳細なエスケープ記法の完全互換は、既存の本文記法対応の後続課題として扱う。
- 保存済みデータだけで解決し、未解決の題名をBacklog APIへ問い合わせたり、通常閲覧で外部データを自動取得したりしない。

## 7. 自己レビューで見つかった本文解析2件の修正計画

### 7.1 再現結果と原因

いずれも優先度P2。`src/archive/render.mjs` の共通本文変換を使うホーム説明、課題説明、全コメント、Wiki本文が修正対象になる。ローカルの完成済み fixture を使った再現では `fetch` の呼び出しは0回だった。既存の render／report テスト10件と構文チェックは通過したが、以下のケースを検証していなかった。

| 不具合 | 再現入力と現在の結果 | 原因 |
| --- | --- | --- |
| 不正な括弧が後続の変換を止める | `[[]] DEMO-2 [[Overview]] #image(401)` がすべて文字のままになる。課題コメントでも再現した | `renderInlineText` が有効な参照にならない `[[` に遭遇すると、残り全体をエスケープしてループを終了する |
| URLを含むWiki題名が分割される | 保存済み題名 `Guide https://example.test/docs` への参照が、末尾の `]]` を含む外部URLになる。未収集の `[[Unknown https://example.test/missing]]` も部分的に外部リンクになる | `renderText` のURL解析がWiki参照の解析より先に実行され、二重括弧の内部で原文を分割する |

### 7.2 本文の認識順序

`renderText` と `renderInlineText` の二段階で原文を分割する構成を見直し、原文の位置を進めながらインライン記法を認識する共通処理にまとめる。既存のWiki名索引、相対パス計算、URLの安全性確認、添付の解決関数は引き続き使う。

1. 原文中で次に現れる記法を認識する。Wiki参照、対応済みのMarkdownリンク／外部画像参照、添付マクロ、単独URLをそれぞれ一まとまりとして扱う。Markdownリンクの表示名・リンク先や添付マクロの内部をWiki参照として再解析しない。
2. `[[` に到達した場合は、その参照をURL処理より先に確定する。正常なWiki参照に含まれるURLや画像マクロ風の文字を、別の記法として処理しない。
3. Wiki題名は従来どおり完全一致と一意性で解決する。未知・重複の題名は参照全体をエスケープして残し、内部のURLをリンクにしない。
4. 取得済みの課題キーだけを内容に持つ `[[DEMO-1]]` は、既存の二重括弧を含む課題リンク表示を保つ。内容全体が単独の安全なURLである二重括弧は既存のURL扱いを優先し、括弧をURLから分離する。表示名付きURLなどの記法を新規に導入しない。
5. 単独URL・Markdownリンクは既存の許可スキーム、認証情報の除去、外部リンク属性、ローカルリンクへの変換条件を維持する。生成済みHTMLを再解析しない。

Wiki参照の題名に含められる文字の範囲は初回実装と同じとし、角括弧や改行を題名の一部として新たに扱わない。現在対応済みのコードブロックは `renderBody` が先に切り分け、今回のインライン解析へ渡さない。

### 7.3 不正な括弧からの復帰

不正な参照の文字は保持し、その後の独立した記法の解析を続ける。段落全体の解析を終了する処理をなくす。以下を具体的な復帰条件として固定する。

- 空の閉じた参照 `[[]]` は、その部分だけを文字として残し、直後から処理を続ける。
- 開いたままの `[[` の後に別の正常な `[[Overview]]` がある場合は、後の参照を認識する。課題キー・コメント参照・添付マクロなど、後続の独立した記法も処理する。
- 既存fixtureの `[[[[Overview]]` は一つの不正な括弧のまとまりとして文字のまま残す。このまとまりの外側に続く正常な参照は処理する。
- 改行を越えてWiki題名を探さず、次の行の通常テキスト・参照と改行表示を保持する。
- 解析位置は毎回必ず進め、参照の欠落・重複出力・停止が起きないようにする。

#### 作業3：括弧の範囲を読む関数を追加する

`src/archive/render.mjs` に内部関数 `readBracketReference(value, start)` を追加する。`value` は原文、`start` は `[[` の先頭位置。戻り値は次のどちらかとする。

```text
正常な閉じた参照：{ kind: 'reference', raw, name, end }
不正な括弧：     { kind: 'literal',   raw,       end }
```

`raw` は原文の対象部分、`name` は二重括弧を除いた題名、`end` は対象部分の直後の位置。全分岐で `end > start` を保証する。閉じ括弧や改行を探す際は、以下の条件に従う。

1. 開き括弧の直後がさらに `[[` なら、隣接する開き括弧のまとまりとして扱う。同じ行を一度走査し、最初の `]]` までを `literal` にする。閉じ括弧がなければ、先頭で連続している `[` だけを `literal` にして、その後の通常テキストを処理できる位置を返す。行末を別に何度も検索せず、各走査位置を前へ進める。
2. それ以外は `start + 2` から原文を順に調べる。最初の `]]` に達したらそこまでを対象とする。内容が空、または内容に単独の `[`・`]` があれば `literal`、それ以外なら `reference` とする。
3. 閉じ括弧より先に別の `[[` に達した場合、先頭の開き括弧2文字だけを `literal` として返す。その後の通常テキストや別の参照は、呼び出し側が続けて処理する。
4. 閉じ括弧より先に改行（CRまたはLF）か文字列の末尾に達した場合も、先頭の開き括弧2文字だけを `literal` として返す。改行をこの関数で消費しない。

この関数はHTMLを生成せず、リンク先の解決も行わない。名前をtrim・デコード・正規化しない。

#### 作業4：二重括弧内の処理を確定する

既存の `renderWikiReference(pageName, reference, links)` を次の順序にする。

1. 保存済み課題キーと完全一致する場合：現在と同じ `renderInternalReferences(reference, links)` を使う。
2. 内容全体が単独のURLの場合：`renderExternalLink(pageName, links)` を使い、正常なリンクが得られればその前後に文字の `[[`・`]]` を付ける。リンクを作れなければ参照全体をエスケープする。
3. それ以外：現在のWiki題名索引による完全一致・一意性判定を使う。

2のURL判定は、次の正規表現による全文一致とする。`Guide https://...` のように題名の途中にURLがある場合は2に該当せず、3へ進む。

```js
/^(?:https?:\/\/|mailto:|\/downloadSharedFile\/)[^\s<>"']+$/u
```

二重括弧のURLの期待HTMLは次のとおり。認証情報の除去やローカル変換は、既存の `renderExternalLink` に任せる。

```html
[[<a href="https://example.test/docs" target="_blank" rel="noopener noreferrer">https://example.test/docs</a>]]
```

#### 作業5：原文を一回の処理順で認識する

`renderText(value, links, attachmentLinks)` に解析位置を持たせる。現在の `renderInlineText` は処理をここへ統合し、参照されなくなった関数を削除する。空の本文に対する既存の戻り値は維持する。

各位置では、次の順に記法の開始を調べる。

1. `[[`：作業3の関数で範囲を確定する。`reference` は作業4へ渡し、`literal` は `escapeHtml(raw)` で出力する。
2. 対応済みMarkdown外部画像参照 `![alt](URL)`：現在と同じ通常リンクにする。外部画像の `<img>` は作らない。
3. 対応済みMarkdownリンク `[label](URL)`：現在と同じ `renderExternalLink(URL, links, true, label)` を使う。
4. 添付マクロ `#image(...)`・`#thumbnail(...)`・`#attach(...)`・`![alt][ref]`：既存の `renderAttachmentMacro` を使う。
5. 単独URL：既存の `splitTrailingUrlPunctuation` と `renderExternalLink` を使う。

2〜5の認識範囲は現在の正規表現を個別に切り出して維持する。解析位置以外で一致させないため、各正規表現にstickyフラグ `y` を付け、実行直前に `lastIndex = position` を設定する。URLの許可スキームやMarkdownの認識範囲を広げない。Markdownリンクの正規表現にある `(?<!!)` も保持する。

添付マクロの正規表現からWiki用の選択肢を除くと、捕捉番号は `renderAttachmentMacro` が元から受け取る1〜6番に戻る。配列の対応は、1=image種別、2=image参照、3=attach名、4=attach ID、5=Markdown alt、6=Markdown参照。現在の捕捉番号2〜7からの詰め替えは不要になる。

解析ループは以下の形にする。`readTokenAt` はその位置で始まる記法だけを返し、HTML化した文字列と対象の直後の `end` を持つ。記法を認識しない場合はnullを返す。

```text
result = ''
position = 0
plainStart = 0
while position < value.length:
    token = readTokenAt(value, position, links, attachmentLinks)
    if token is null:
        position += 1
        continue
    result += renderInternalReferences(value.slice(plainStart, position), links)
    result += token.html
    position = token.end
    plainStart = position
result += renderInternalReferences(value.slice(plainStart), links)
return result
```

通常テキストは `renderInternalReferences` へ渡すので、課題キー・コメント参照と既存の改行表示を保てる。不正な閉じた参照の内部は `literal` として一括出力し、その中にある課題キーを再解析しない。単独URLの末尾記号はエスケープしてリンクの後へ出すが、`end` は元の一致範囲の直後に置き、記号を二重に出力しない。
